Comparison: claude-orchestrator vs claude-conductor

Architecture Overview

Aspect claude-orchestrator claude-conductor
Queue Backend SQLite + in-memory Bull Queue (Redis)
Processing Model Custom orchestrator loop (10s cycle) Bull worker with event-driven processing
Batching Area-based grouping (2-5 tickets) No batching (single job execution)
Concurrency Slot-based (3-10 worktrees) Sequential (single Bull processor)
State Machine Custom implementation Bull's built-in job states

1. Exponential Backoff Retry Strategy ✅ IMPLEMENTED

claude-conductor approach:

backoff: {
  type: 'exponential',
  delay: 5000  // 5s → 10s → 20s → 40s
}

Previous claude-orchestrator: Fixed delays (2s, 30s, 2min) with irregular jumps.

✅ Now Implemented (PR #8): 
calculateBackoffDelay(attemptCount, baseDelay=5000, factor=2, max=120000)
// Attempt 1: 5s → Attempt 2: 10s → Attempt 3: 20s → Attempt 4: 40s

Features:

  • Smooth exponential scaling - No more irregular jumps
  • Error-specific base delays - Integrates with error categorization
  • 30 comprehensive tests - Full test coverage with 54 assertions
  • Adaptive timing:
    • Build/lint errors: 10s base (quick fixes)
    • Test failures: 30s base (standard retry)
    • Timeouts: 60s base (system recovery)

2. Iterative Feedback Loop for Failed Tasks ✅✅ IMPLEMENTED

claude-conductor's killer feature: The Iterative Factory system analyses failures and generates structured feedback for the next attempt:

IterationFeedback {
  error_analysis: string
  improvement_suggestions: string[]
  code_changes_needed: string[]
  retry_strategy: 'fix_dependencies' | 'fix_code' | 'fix_config' | 'change_approach' | 'abort'
}

Previous claude-orchestrator: Simply respawned with the same prompt after failure.

✅ Now Implemented (PR #7): Created failure-analyzer.ts module with comprehensive log analysis

Features:

  • 10+ error pattern detectors:
    • Syntax errors (SyntaxError, Unexpected token)
    • Runtime errors (TypeError, ReferenceError)
    • Test failures (FAIL, Expected vs Got)
    • Build failures (Compilation error, Module not found)
    • Git errors (merge conflicts, rebase failures)
    • Tool usage errors (Edit tool failures, old_string not found)
    • Dependency errors (npm ERR!, missing modules)
    • Permission errors (EACCES, EPERM)
    • Timeouts and environment errors
  • Repeated pattern detection - Identifies when agent is stuck in loops
  • Category-specific suggestions - Tailored advice per error type
  • Severity assessment - Low, Medium, High, Critical
  • Integrated into retry prompts - Agents receive structured failure analysis with prominent warnings about repeated failures

Example feedback to agent:

## Failure Analysis from Previous Attempt:

**Category:** test_failure
**Severity:** high
**Root Cause:** 3 unit tests failing in auth module

⚠️ Warning - Repeated Patterns Detected:
  - Edit tool failed 3 times (old_string not found)
  - Same test continues to fail after modifications

These approaches are NOT working. You must try something fundamentally different.

**Actionable Suggestions:**
  • Use Read tool to verify file contents before using Edit
  • Check test expectations don't match actual implementation
  • Try running queue-run test npm test locally to see full output

3. Error Categorisation ✅ IMPLEMENTED

claude-conductor classifies errors:

  • dependency_missing
  • syntax_error
  • timeout
  • file_permission
  • runtime_error

Previous claude-orchestrator: Generic failure handling, no categorisation.

✅ Now Implemented (PR #7): Created error-types.ts with comprehensive categorization

11 Error Categories:

  • ci_test_failure - Tests failed (30s cooldown, escalate after 2 attempts)
  • ci_build_failure - Build/compilation failed (10s cooldown, escalate immediately)
  • ci_lint_failure - Lint/format issues (10s cooldown, no escalation)
  • ci_timeout - CI took too long (60s cooldown, always escalate)
  • review_score_low - Review bot scored < 90 (30s cooldown)
  • merge_conflict - Conflicts with dev branch (10s cooldown, escalate after 2)
  • dependency_error - Missing packages (30s cooldown)
  • permission_error - Git/filesystem permissions (60s cooldown, always escalate)
  • agent_timeout - Agent didn't complete (60s cooldown, always escalate)
  • agent_crash - Agent process crashed (30s cooldown, escalate immediately)
  • unknown - Unclassified errors (30s cooldown)

Smart Retry Logic:

  • Retryable flag - Determines if retry is worthwhile
  • Suggested cooldown - Error-specific delay timing
  • Escalate model flag - When to use Opus instead of Sonnet
  • Requires human flag - When to flag for manual intervention
  • Severity levels - Transient, Fixable, Critical

21 comprehensive tests - Full coverage of categorization logic

4. Job-Level Resource Limits

claude-conductor: Per-job memory/CPU limits in Docker config.

Current claude-orchestrator: No per-ticket resource management (relies on Claude CLI defaults).

Lower priority - less applicable since you're spawning Claude CLI processes, not containers.

5. Structured Progress Events ✅ IMPLEMENTED

claude-conductor emits granular progress:

'job.progress' // 10%, 25%, 50%, 75%, 90%, 100%

Previous claude-orchestrator: Binary state (running/not running) + log streaming.

✅ Now Implemented (PR #6): Created progress-tracker.ts with real-time phase detection

6 Progress Phases:

Phase Progress Triggered By
analyzing 10% Read, Grep, Glob tools
planning 25% TodoWrite tool
coding 50% Edit, Write tools
testing 70% npm test, queue-run test
pr_creation 90% gh pr create, git push
complete 100% Agent exits successfully

Features:

  • Real-time WebSocket broadcasts - UI updates immediately
  • Lightweight pattern matching - Minimal performance overhead
  • Backward compatible - Works with existing agents
  • Database persistence - Progress saved to DB (progress_phase, progress_percent columns)

This significantly improves UI feedback - users can now see exactly what stage each agent is at!

6. Stale Session Cleanup ✅

claude-conductor: Auto-cleanup of sessions after 5 minutes post-completion, with 60-second stale check interval.

Current claude-orchestrator: Has stale detection but cleanup could be more aggressive.

Recommendation: Already implemented reasonably well, but could add automatic archival of tickets stuck in limbo states.
